Create embeddings

curl {{BASE_URL}}/v1/embeddings \
  -H 'Content-Type: application/json' \
  -d '{"model":"{{MODEL_ID}}","input":["How do I cool a laptop?"],"task":"retrieval.query","dimensions":512}'

Text accepts a string, an array of strings, one token-ID array, or an array of token-ID arrays. The standard model, dimensions, encoding_format, and user fields are accepted, plus the retrieval role (below). dimensions selects a Matryoshka size ({{MATRYOSHKA}}; default {{DIMENSIONS}}): the vector is truncated and re-normalized. Unknown fields are rejected. Each text may use up to {{MAX_TOKENS}} tokens including its retrieval prompt and is never truncated; a request may use {{MAX_REQUEST_TOKENS}} tokens across all inputs. encoding_format supports float or little-endian float32 base64. Responses carry X-Glossematics-Space, X-Glossematics-Dimensions, and X-Glossematics-Role, plus X-Glossematics-Video-Recipe when the request had a video input (see Media); usage counts text tokens including the prompt, and media items count zero (X-Glossematics-Usage-Scope).

Short texts from concurrent requests are collected for {{BATCH_WINDOW_MS}} ms into the model's native batch functions (64 rows up to 32 tokens, down to 4 rows up to 512 tokens); longer texts run alone.

Queries and documents

The model is asymmetric: a text is prefixed with Query: or Document: before encoding, and media are wrapped with the same role. Set the role with "task" (retrieval.query or retrieval.passage), "role", or "input_type" (query, document, passage). It applies to every input in the request.

Default: document. Embed search queries with "task":"retrieval.query" and the corpus without a role (or retrieval.passage). Only retrieval conditioning is available in this bundle. Token-ID inputs are embedded exactly as given, with no prompt added.

Compute

Placement is chosen per function by the runtime ({{COMPUTE}}): short text buckets (up to 128 tokens) and short media sequences run on the Neural Engine, longer text and the vision, audio, and video towers on the GPU. The --compute flag applies to BidirLM bundles only.

Media

Loaded modalities: {{MODALITIES}}. OpenAI does not define media input for embeddings, so Glossematics accepts explicit content objects with base64 data URLs. Each item returns one vector in the same space as text:

{"model":"{{MODEL_ID}}","input":[
  {"type":"input_image","image_url":"data:image/png;base64,iVBOR..."},
  {"type":"input_audio","audio_url":"data:audio/wav;base64,UklGR..."},
  {"type":"input_video","video_url":"data:video/mp4;base64,AAAAI..."}]}

Images accept PNG, JPEG, and WEBP up to 20 MiB and are resized to 0.26-1.3 megapixels. Preprocessing follows the source processor: smart-resize rounds half to even, audio has ceil(samples / 160) mel frames, and multichannel audio is averaged to mono. Audio accepts WAV up to 20 MiB and 30 seconds, resampled to 16 kHz mono; a clip shorter than 480 samples at 16 kHz (30 ms) has no audio token and is rejected. Video accepts MP4 up to 32 MiB and 60 seconds, sampled at 2 frames per second (4 to 32 frames) within the tower's 2048-patch budget; each source frame may be at most 4096 pixels on either edge and 4096 × 4096 (16.8 million) pixels, checked before any frame is decoded. Interleaved message inputs are not supported by this model and are rejected with unsupported_modality, as are modalities the loaded bundle does not include. Remote URLs and local paths are never fetched.

Decoding, resizing, and mel extraction run on a bounded CPU pool, off the accelerator: only the Core ML predictions hold the accelerator, so a multi-second video decode never blocks text or other media. Audio and video uploads are staged in per-request temporary files that are removed when preparation ends; a bad input returns 400 naming its position in input.

Video recipe. Video vectors from different decode and sampling recipes share a space ID but are not comparable. A response whose request had a video input carries X-Glossematics-Video-Recipe, the value /health reports as video_recipe; store it with the vectors and re-embed video when it changes. Text-only requests do not carry it.

Startup and resilience

Startup verification. --startup-verification full|basic (default full) sets what runs before /ready turns green. full loads and runs every Core ML function once: all text buckets and batch rungs, every image, video, and audio encoder bucket, and every embed and decoder bucket (41 functions in the production bundle). Each output must be finite, correctly shaped, and unit-norm, and functions that must agree are cross-checked with chip-independent consistency: one text through every text bucket, each batch rung against the single-row function, one procedural image, video clip, and audio clip through every encoder bucket. The functions stay resident, so serving starts warm; readiness takes longer (seconds on a warm machine, minutes on the first start while Core ML compiles). Each function is logged as it finishes. basic runs one warm text embedding, as before.

If any function fails, the server does not become ready: /ready stays 503 with status failed, the log and error name the first failing function and why, and the process stays up for inspection. /health reports startup_verification (mode, functions, passed, failed, first failure, minimum consistency cosine, wall time, footprint growth) and the chip and macos it runs on: batch thresholds were calibrated on an Apple M4 Max, so re-run make bench on other silicon. The keep-warm loop runs the single warm embedding only.

Failure isolation. Rows from unrelated requests share a text batch. If a batch fails, each row is re-run alone on the single-row functions while the accelerator is still held; only the requests whose own rows fail get an error, and the rest complete in order. Retries are counted in gloss_text_isolation_retries_total and gloss_text_isolation_failed_rows_total.

Temporary files. Before the listener opens, the server removes gloss-media-* upload directories that a crashed or killed process left in the temporary directory (dead owner, or old), and logs how many.

Source revision re-pin (87f7a45d). This release changes every Jina space ID, at every output size: the source revision is part of the space identity, and it was re-pinned to the snapshot actually converted, 87f7a45d1ae0265843f8569c47fb53847cb193c3, because the old pin, 41a20a1e, no longer resolves on the Hub. Model weights and the manifest spaceID string are unchanged. Existing Jina indexes must be re-embedded. This cleanly absorbs the preprocessing fixes in this release (image rounding, audio frame count, stereo downmix), so old and new vectors never share a space.

Cutover. This binary refuses bundles pinned to 41a20a1e, and older binaries refuse re-pinned bundles. Install the new binary together with a re-pinned bundle, for example make install BUNDLE=<re-pinned bundle>, and expect the roughly 7-minute startup verification before /ready turns green.
